# 01 · 系统架构设计文档

| 文档版本 | v1.0 | 软件版本 | v1.0.0 | 日期 | 2026-09-14 |
|---|---|---|---|---|---|

## 1. 架构目标与设计原则

1. **headless 单二进制**：Go 静态编译、前端 `go:embed` 内嵌、SQLite 纯 Go 驱动（CGO-free），目标机无浏览器、无 Node、无外网、无外部中间件即可运行。
2. **配置即数据、热生效**：业务配置（飞连接入参数、通道、绑定）全部持久化到 SQLite，经不可变快照整体替换实现无锁读与即时生效，变更无需重启。
3. **厂商无关 + 表单化**：以「字段映射表 + 签名片段构造器 + 响应/回执路径映射」描述任意 JSON-over-HTTP 厂商，禁止手写 JSON 模板，新厂商接入零代码。
4. **面向失败的可靠性边界**：对飞连始终快速回 200，下游失败只留痕不引发重推；以 `appSmsId` 为幂等键，终态不重发，崩溃残留 pending 按阈值补发一次。
5. **分层与单向依赖**：入站适配 → 编排 → 领域引擎 → 持久化，依赖方向单一，可逐层表驱动测试。
6. **安全内建**：密钥信封加密、最小权限 systemd、网络边界访问控制、日志出口统一脱敏。

## 2. 技术选型

| 持久化 | SQLite（modernc.org/sqlite v1.58.0，纯 Go） | 零运维、单文件、CGO-free 交叉编译 |

| 唯一标识 | github.com/google/uuid v1.6.0 | 通道 ID 生成 |

## 5. 核心数据流

### 5.1 短信事件转发主链路（成功路径）

```
飞连 POST 事件
  │ httpapi.dispatchRoot（POST 兜底）
  │   └─ 路径 == settings.WebhookPath()（运行时比对，故可热改）
  │   └─ 读 body（≤1MiB）→ resolvePlaintext（按 EncryptKey 决定解密/拒绝降级）
  │   └─ ParseChallenge？是→token 恒定时间校验→JSON 原样回 challenge（application/json，<1s）
  │   └─ 非短信事件→记日志→200
  │   └─ ParseEnvelope→header.token 校验（失败 401，零编排动作）
  ▼
ForwardService.HandleEvent(eventID, objects[])         （逐条，批量键 event_id-i）
  for each object:
   1. 幂等闸门 GetSend(appSmsId)
        终态 success/failed            → skipped（不重发）
        pending 且未超 stale 阈值       → skipped（在途不重复）
        pending 超阈值                  → 续发（沿用原行）
        无记录                          → 继续
   2. buildPlan：快照内查绑定→通道；停用/未绑定/通道缺失→降级计划
   3. InsertPendingIfAbsent（脱敏手机/参数落 pending）
   4. 降级？→ MarkFailed(unbound/disabled/...)→下一条
   5. cfg.Render：变量→号码归一化→签名（先签名）→映射组装 JSON→头插值
   6. Client.Do（context 超时=当前设置 downstream_timeout_ms，热生效）
   7. ParseSendResult：success_path 宽松相等判定；提取 msg_id/message
   8. MarkSuccess / MarkFailed(vendor|network|timeout|render|invalid_mobile)
  ▼
httpapi 记录汇总日志（event_id/total/succeeded/failed/skipped/elapsed_ms）
  └─ 恒回 200 {"code":0,"message":"success"}（任何单条失败都不改变响应）
```

要点：飞连仅以 HTTP 状态决定是否重推，因此**除 token 不符（401）、报文不可解析/应解密无 key（400）、路径不存在（404）、超 1MiB（413）外，业务结果一律 200**。

### 5.2 厂商异步回执链路

```
厂商 POST /receipts/{channel_id}
  └─ 回执 Token 鉴权（系统设置了才校验：X-Receipt-Token 头或 ?token=，恒定时间比较；
       缺失/不符直接 401，先于读 body 与通道查找）
  └─ 读 body（≤1MiB）→ 取直连 RemoteAddr（不读 XFF）
  └─ ReceiptService.Handle：
       快照定位通道（缺失→404）→ 解析回执配置
       JSON 解码（UseNumber）→ 按路径提取 appSmsId/smsId/status/statusMessage/seqNo
       status == delivered_value（示例厂商 DELIVRD）→ delivered
       status == failure_value（示例厂商 UNDELIV）→ delivery_failed
       其余中间态值不改送达状态，仅推进 seq_no 地板
       ApplyReceipt 三重守卫（通道归属/seq 单调/delivered 不回退）后回写
       delivery_*（不改主 status）；未知 appSmsId 仅 found=false 不报错
  └─ 原样回通道配置的成功响应（默认示例厂商 {"status":0,"message":"success"}）
```

### 5.3 配置热加载链路

```
WebUI/API 写配置 ─▶ Store 在短事务内提交（写串行锁 writeMu，单连接）
                        │ 提交后 notifyChanged()
                        ▼
                 Cache 回调：从库全量重载 settings+channels(解密)+bindings
                        │ 构造新的不可变 Snapshot（含版本号）
                        ▼
                 原子替换内部指针（RLock/Lock 保护）
请求处理侧：SettingsRuntime/Cache.Current() 每次 O(1) 读当前快照
  → Verification Token、webhook 路径、超时、通道映射/密钥/绑定均「下一条请求生效」
```

## 6. 关键设计决策

### 6.1 幂等状态机（崩溃安全）

```
              InsertPendingIfAbsent            厂商成功判定
  (无记录) ───────────────────────▶ pending ──────────────────▶ success（终态）
                                       │  │
                  配置降级/渲染失败 ───┘  └──── 网络/超时/业务失败
                   非法号码                            ▼
                                                     failed（终态）
  回执只回写 delivery_status/delivery_message/seq_no/receipt_at，不改变主 status。
```

- 幂等键 `appSmsId`：单事件取飞连 `event_id`；批量取 `event_id-下标`；长度 ≥64 拒绝下发。
- 传输类失败（网络错误/超时/5xx/429）保持 pending，由后台补发 worker 每 30 秒扫描一批（≤100）超过 `stale_pending_ms` 的在途记录：以 `updated_at` CAS 认领（飞连重推与 worker 单飞），按最新快照刷新路由并解密 `payload_enc` 重放；首次下发不计，最多续发 3 次，仍未确认置 failed/`resend_exhausted`。业务类失败（4xx 非 429、2xx 业务拒绝）为终态；成功/失败终态永不重发。
- 测试发送使用 `test-<毫秒>-<随机>` 幂等键并标 `source=test`，与飞连流量隔离可筛。

### 6.2 字段映射引擎（通用通道核心）

- 每条映射四元组：`target`（点分路径，数字段为数组下标）、`source_type`（variable/const/literal）、`source`、`value_type`（string/number/boolean/raw）。
- 引擎用映射表确定性构建嵌套 `map`，数字路径自动扩切片，最后 `json.Marshal`，天然保证合法 JSON；重复 target、标量/容器冲突、非法变量、值类型转换失败均报错。
- 渲染顺序固定为**先生成 nonce/timestamp 与变量 → 计算签名 → 再组装请求体**，故字段映射行可引用 `sign` 变量。
- 保存前以样例输入执行一次「试渲染」（不发真实请求），把错误定位到具体配置区块/字段；仅「密钥尚未填写」放行（预置脚手架态）。

### 6.3 签名策略可注册

- `none`：不签名；`sha1_salt`：`lowerHex(SHA-1(appSecret || 待签名串))`；`hmac_sha256`：hex/base64 输出可选。
- 待签名串由有序「字面量片段 + 变量片段」构造，示例厂商预置固定 6 片段拼成 `timestamp=<ts>&nonce=<nonce>&signData=<appSmsId>`。
- 示例厂商策略以独立 JDK 参考程序产生的双端向量（含摘要字节补零、非 ASCII、空 nonce、6 位 nonce）在 Go 侧逐字节固化验收。

### 6.4 密钥信封加密

- 通道密钥（如示例厂商 appSecret）以 **AES-256-GCM** 加密：每次随机 96bit nonce，落库为 `base64(nonce || ciphertext||tag)`，存于 `channel_secrets`，与明文通道配置分离。
- 主密钥 data key（32 字节）来源：环境变量 `SMSGW_SECRETS_DATA_KEY`（优先生效、不落盘）或密钥文件（首启自动生成，0600/0640）；不进库、不进 Git。
- API 与界面仅返回掩码与「是否已设置」；空提交=不修改；密钥名必须先在通道常量中声明为 `secret`，否则拒绝写入。

### 6.5 日志出口统一脱敏（zapcore.Core 装饰器）

不在每个调用点手工脱敏，而是包装 `zapcore.Core`（同时实现 `With/Check/Write`）：

- **字段名层**：secret/password/token/sign/signature/authorization/auth/key/credential 等词表（先整键后分词匹配，避免误伤 `design`、`param_index`）整值替换为 `[REDACTED]`；`params/paramN` 整体掩码。
- **值文本层**：对字符串、error、Stringer、ByteString 字段及消息/堆栈文本跑手机号正则兜底；手机号按**前 3 后 2 等长星号**掩码并保留 86 前缀，正则带数字边界校验避免误伤毫秒时间戳。
- 因脱敏位于出口 Core，未来新增日志点自动受保护；测试以 observer 挂在脱敏 Core 下游断言「实际落盘内容」，并经变异测试验证断言有效。

### 6.6 恒 200 与超时预算

- 单次下发 `context.WithTimeout(settings.downstream_timeout_ms)`（默认 2000ms，范围 100~60000，热生效）；HTTP 客户端另有 60s 硬上限防止反向压缩热配置。
- 超时/5xx 归 `network`/`timeout`，2xx 业务拒绝归 `vendor`；无论哪种，webhook 均 200，配合幂等闸门实现「失败不重推、可查可补」。

## 7. 并发与事务设计

- HTTP server 每请求独立 goroutine；`ReadHeaderTimeout=10s`、`ReadTimeout=30s`、`IdleTimeout=120s`（不设 `WriteTimeout`，webhook 按下游超时预算同步等待批量下发）；SIGTERM/SIGINT 先 `Shutdown` 接入层（6 秒排空在途）再停止后台补发 worker（4 秒），共 10 秒宽限期，最后关闭 SQLite。
- SQLite：`SetMaxOpenConns(1)` 使写天然串行，另以 `writeMu` 串行化写事务；PRAGMA `journal_mode(WAL)`、`busy_timeout(5000)`、`synchronous(NORMAL)`、`foreign_keys(ON)`，短事务，消除 SQLITE_BUSY 并保证崩溃一致性。
- 配置快照不可变、整体替换，读路径仅 RLock；密钥明文只存在于内存快照，不落日志。

## 8. 安全设计

| 面 | 措施 |
|---|---|
| 传输边界 | 内网 HTTP，不做 TLS；管理面不做来源 IP 限制，依赖网络分区与边界访问控制（安全组/防火墙/堡垒机/反代 ACL） |
| 来源校验 | Webhook `header.token` 与设置恒定时间比较；不符 401 且零下游调用 |
| 密钥存储 | AES-256-GCM 密文、主密钥环境变量/0600 文件、掩码回显、空提交不修改、不进 Git |
| 日志脱敏 | 出口 Core 强制脱敏手机号/params/secret/sign/鉴权头（见 6.5） |
| 输入约束 | 请求体 ≤1MiB；方法白名单 POST/GET/PUT；webhook 路径/URL/阈值字段级校验；批量绑定全量校验后才写库 |
| 响应约束 | 统一 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`；500 不外泄内部错误详情 |
| 主机加固 | systemd 专用 nologin 用户、目录 0750、NoNewPrivileges、ProtectSystem=full、清空 capability、RestrictAddressFamilies 等 |
| 回执 | 可选全局共享 Token（`X-Receipt-Token` 头/`?token=`，恒定时间比较，空=不校验），鉴权先于报文与通道解析；记录来源直连 IP；签名式验签预留扩展位 |

## 9. 可观测性

- Zap JSON（生产）/console（排障），标准字段：level/ts/caller/msg。
- 覆盖路径：启动/停止、系统设置更新、通道增删改/预置创建/启停、事件处理汇总（标识 ID 与耗时）、单条短信结论（成功/跳过/失败 + error_kind）、回执、测试发送、加解密失败。
- 结构化业务字段仅含标识类：`event_id/app_sms_id/channel_id/sms_type/outcome/provider_msg_id/delivery_status/error_kind/elapsed_ms/remote_ip`；**绝不含手机号、params、密钥、签名**。
- 日志交 journald：`journalctl -u sms-gateway -f`。`GET /health` 与 `GET /api/health` 返回 `{"status":"ok"}` 且 no-store，前端每 20s 以 XHR 静默探活。

## 10. 进程启动与关闭时序

启动（`cmd/sms-gateway/main.go`）：
`引导配置 Load → 日志 logging.New → 解析 data key → store.Open(迁移) → NewCache(首次快照) → SettingsRuntime → channel.Client → Forward/Receipt/TestSend 服务 → webui.Handler → NewServer(注册路由) → ListenAndServe`。
任一步前置失败以中文错误快速失败（panic/Fatal），不带病启动。

关闭：收到 SIGTERM/SIGINT → 记录优雅关闭日志 → `httpSrv.Shutdown(5s)` 停止接收新连接并等待在途请求 → 超时则 `Close()` 强关 → 关闭 Store → 日志 Sync。

## 11. 可扩展性

- **新厂商（JSON over HTTP + 现有签名策略）**：全程 WebUI 表单完成，无需发版；也可在代码中仿照 `preset_builtin.go` 增加内置预置后再发版。
- **新签名算法**：实现 `channel/sign.Signer` 并在注册表登记，表单与存储模型不变。
- **新回执验签**：在通道回执配置区扩展，回执服务结构已隔离。
- 明确不支持（超出本期）：XML/SOAP、form 报文、厂商私有 TCP、多通道故障切换、HA 集群。
